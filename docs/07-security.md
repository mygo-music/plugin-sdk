# 07 · 安全模型

插件是第三方代码,市场对任何人开放提交。设计假设是:**插件可能有恶意或有 bug。** 沙箱与权限的目标是把它能造成的伤害限制在它声明过的范围里,并让用户在安装前看到这个范围——**不是**让用户完全不必担心(见 §7.7)。

## 7.1 威胁与对策

| 威胁 | 对策 |
|---|---|
| 读写用户文件、环境变量、启动进程 | WASM 沙箱:没有预打开的目录、没有环境变量与参数、没有进程 API(§3.1) |
| 访问任意网络、把数据发往任意服务器 | 网络只能走宿主函数 `http.do` / `http.batch`;主机必须在 `network.hosts` 内(§7.2) |
| 把宿主当作跳板访问内网(SSRF) | 目标解析一次,拨号时检查实际 IP:拒绝环回、私网、链路本地等(§7.3) |
| 读取其他插件的会话与凭据 | 保险库、cookie 罐、kv 全部按插件 ID 隔离;API 里没有「指定插件」的参数 |
| 通过返回的流/封面地址让宿主访问任意主机 | 宿主获取的资源也受 `media.hosts` 与同一套目标校验限制,并且不带 cookie(§7.2) |
| 伪造登录界面诱导用户输入密码 | 登录界面总是宿主的原生控件,插件无法画自己的框。**但用户提交的字段值会交给插件**(§7.7)——所以登录要靠信任插件的来源,而不是靠沙箱 |
| 拖垮或崩溃宿主 | 内存、时间、响应体、并发、日志速率都有上限(§3.7);超限或陷阱只丢弃该实例;睡眠与宿主函数可被取消(§3.1) |
| 更新后偷偷扩大权限 | 新增主机、`local`、新能力、新的写操作特性、新的授权字段,都需要用户重新确认(§7.5) |
| 恶意更新(供应链) | 市场对每个版本固定 sha256;发布必须带 GitHub 构建来源证明;可吊销(§7.6)。**这不能防住作者账号被盗**(§7.7) |
| 输出里夹带脚本 | 所有插件文本按纯文本渲染;宿主不解析 HTML/Markdown;非 http(s) 的图片地址一律拒绝 |

## 7.2 网络权限

两类权限,故意分开:

| | `network.hosts` | `media.hosts` |
|---|---|---|
| 谁发请求 | 插件(通过 `http.do` / `http.batch`) | 宿主(下载封面、头像、音频流) |
| 带 cookie | 是(插件的 cookie 罐) | **否** |
| 内容 | API | 图片、音频 |

分开的好处:封面、音频的 CDN 域名通常又多又杂(`*.music.126.net`),放进 `network.hosts` 会让插件能带着会话 cookie 向这些域名发请求;分开后,宿主**自动**附带的 cookie 只会发给声明的 API 主机。

**这不等于「会话 cookie 绝不会流向别处」。** 插件能用 `cookie.list` 读出自己的 cookie,再把它放进 `http.do` 的请求(只会发往 `network.hosts`),或者放进 `Stream.headers` / 图片地址(发往 `media.hosts`)。所以 `media.hosts` 同样应当尽量窄:它是插件向外送数据的第二条通道(§7.7)。

匹配规则(`example.com` / `*.example.com` / `http://example.com`)见 [02 号文档](02-manifest.md#24-权限),规范化与校验见 §7.3。**每一次**请求以及**每一次重定向**都重新匹配。`Stream.headers` 里的 `Range`、`Host`、`Transfer-Encoding`、`Cookie`、`Proxy-*` 会被宿主剔除。

## 7.3 网络目标的校验

对插件触发的每一个网络目标(`http.do`、`http.batch`、`Stream.url`、图片地址),宿主按同一套规则处理:

**解析与规范化(只做一次,之后一律使用这份结果):**

1. 用标准 URL 解析器解析。**拒绝**含用户信息(`user@host`)、含非默认端口(授权来源除外,见 [02 §2.5](02-manifest.md#25-用户设置))、非 `http(s)` 协议的地址。
2. 主机名转小写,去掉**一个**末尾的点,再做 IDNA 的 ToASCII(punycode);之后才与 `network.hosts` / `media.hosts` 比较。比较的是规范化后的主机名,用的也是这份解析结果去发起请求——不再重新解析原始字符串。
3. 主机是 IP 字面量(含 `0x7f.1`、`2130706433` 这类整数/十六进制写法、IPv6 与区域标识)→ 拒绝,除非来自 `network.local` 或用户亲手输入的授权来源。
4. 通配符(`*.example.com`)匹配一个或多个子域标签,不匹配 `example.com` 自身。通配符的基础部分不得是公共后缀(`*.github.io`、`*.co.uk` 之类);宿主在加载 manifest 时用公共后缀列表检查,登记处 CI 同样检查。

**拨号时检查实际 IP**(防 DNS 重绑定):在 `net.Dialer.Control` 里检查每一个真正被拨的地址,而不是只检查解析结果。

- 拒绝:`0.0.0.0/8`、`127.0.0.0/8`、`::1`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`(含云元数据)、`100.64/10`、`198.18/15`、`240/4`、`fc00::/7`、`fe80::/10`、组播、未指定地址。
- IPv4-mapped(`::ffff:a.b.c.d`)与 NAT64 地址先还原成 IPv4,再按上面检查。
- 例外:manifest 的 `network.local: true`,或用户亲手输入的授权来源。这两种情况下安装/保存时都有醒目提示。
- 重定向:每一跳重新做上面全部检查;**拒绝 https→http**。

**代理。** 经代理时,`Dialer.Control` 看到的只是代理的地址,目标由代理解析,上面的检查会被绕过。所以:

- 宿主**自己解析**目标并检查 IP,然后让代理 `CONNECT` 到**检查通过的 IP 字面量**(TLS 的 SNI 与证书校验仍用主机名);
- 做不到这一点的代理配置(如只支持按主机名转发的 SOCKS),插件的流量**不走代理**,并在设置里提示「插件流量未经代理」。

这一条与用户本地代理(例如监听在 `127.0.0.1` 的代理软件)共存,必须在实现时实测(总览 §1.8 S7)。

## 7.4 数据隔离与存储

```
<UserData>/plugins/<id>/<version>/        包内容(manifest.json、plugin.wasm、icon.png)
<UserData>/plugins/<id>/data/kv.json      kv 存储(≤ 1 MiB)
<UserData>/plugins/<id>/data/vault.bin    保险库:secret、cookie 罐、password 类设置(AES-256-GCM)
系统钥匙串  条目 "mygo-music/vault-key"     一把 256 位密钥,解开所有插件的保险库
```

**为什么不把 secret 和 cookie 罐直接放进系统钥匙串。**

- 框架的 `Secrets.Set` 单条上限是 2560 字节(Windows 凭据管理器的限制)。一个完整的网易云 cookie 罐(`MUSIC_U`、`NMTID`、`__csrf`、`MUSIC_R_T` 等,连同域、路径、过期时间)很可能超过它,而 4 KiB 的规范值本来就放不下。
- 应用没有 Developer ID,macOS 上每个新版本的 ad-hoc 签名都不同,钥匙串条目的访问权限绑定在签名上,于是**每个条目**在每次升级后都会各弹一次授权。每个插件最多 64 个 secret 加一个 cookie 罐,会弹出一长串。
- Linux 没有 Secret Service 时,钥匙串不可用(框架返回 `errors.ErrUnsupported`)。

**做法。** 每个插件有一个加密文件 `vault.bin`(AES-256-GCM,随机 nonce,每次写入换 nonce),明文是 secret、cookie 罐与 `password` 类设置。解开所有保险库的密钥只有一把,放在系统钥匙串的**一个**条目里——所以升级后最多弹一次授权。

- **没有钥匙串时**(`ErrUnsupported`),密钥放在用户数据目录下权限为 0600 的文件里,并在设置里显示一条持续的提示「凭据没有放进系统钥匙串」。
- **开发构建**(`mygo.IsDev()`)同样用文件放密钥,沿用现有做法,避免每次重新签名都弹授权。
- 同一系统用户下的其他本机程序读得到钥匙串或同一文件时,同样读得到这些凭据——这是任何桌面应用共有的限制(§7.7)。
- 卸载插件时询问是否同时删除它的数据与会话;默认删除。**宿主不会把任何插件数据上传到任何地方。**

**设置的存放。** 插件的用户设置(包括授权来源)保存在**宿主拥有**的存储里,不是插件的 kv:插件读得到,但**写不了**。授权只能来自用户在设置界面里的编辑(见 [02 §2.5](02-manifest.md#25-用户设置))。

## 7.5 权限变更与同意

| 事件 | 行为 |
|---|---|
| 首次安装(市场) | 对话框列出:名称、作者、来源层级(官方/社区)、能力、特性(尤其是会改动账号数据的)、**网络主机**、是否访问局域网 |
| 首次安装(URL) | 同上,外加醒目提示「此插件未经市场审核」,并展示仓库地址 |
| 更新,权限与特性不变 | 静默更新(用户可在设置中改为手动) |
| 更新,**需要重新确认**的变化 | 对话框展示**差异**,用户同意前继续使用旧版本(见下) |
| 更新,权限缩小 | 静默更新 |

**需要重新确认的变化**,按「覆盖范围」比较,不是比较字符串:

- `network.hosts` / `media.hosts` 里**新覆盖**了原来没覆盖的主机(`*.example.com` 覆盖 `a.example.com`;`http://x` 比 `x` 多覆盖明文)。
- `network.local` 变为 `true`。
- 新增能力;新增会改动账号数据的**特性**:`like`、`playlist.edit`、`playlist.subscribe`、`follow`、`podcast.subscribe`、`comments.like`、`radio.dislike`。
- 新增 `grant_network` 设置项或 `password` 类设置项。
- 名称、图标、作者、仓库地址变化(防止一个已上架的插件改名后冒充别人)。

## 7.6 供应链

**对每个版本:**

1. **sha256 固定。** 市场的 `index.json` 记录每个版本的 `.mgp` sha256;宿主下载后校验,不一致则拒绝并报告。注意这只校验**包**:索引本身由谁提供就由谁说了算(见 §7.7)。
2. **构建来源证明。** 市场要求 `.mgp` 带 [GitHub 构建来源证明(artifact attestation)](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations)。登记处 CI 用 `gh attestation verify` 验证,并**固定**这些参数(实现时对照当时的文档核对确切的参数名):仓库(`--repo`)、发布工作流(`--signer-workflow`)、标签引用(`--source-ref refs/tags/v<版本>`)、`--deny-self-hosted-runners`。SDK 模板的发布工作流默认就会生成它。
   - **它证明的是**「这个字节串是由该仓库的该工作流在该标签上构建出来的」。**它不证明**这个 wasm 与仓库里的源码对得上:对仓库有写权限的人可以让工作流为任意字节生成证明。所以评审要看**发布标签上的源码**,并且最好能复现构建。
3. **仓库身份固定。** 登记时记录仓库的数字 ID 与所有者的数字 ID;层级(官方/社区)由**所有者 ID** 判定。仓库改名、转让、被抢注同名仓库时,按 ID 比对会发现。
4. **可吊销。** `index.json` 的 `revoked` 列出被撤下的版本;宿主刷新索引时(最长约 6 小时一次)发现已安装的插件被吊销,**停用**并提示用户。

**URL 安装**不经过登记处,因此没有 1、3、4 的保护。宿主会校验 `.mgp` 的结构与 manifest,显示权限,并**强提示**风险。宿主在 v1 不自己验证来源证明(是否验证留待实现时评估),所以 URL 安装的包不会被标为「已验证」。

## 7.7 残余风险(明确写出来)

沙箱和权限不能解决的:

- **插件可以对声明的主机发送它能访问到的任何数据**——包括它自己的会话、cookie,以及用户在它的表单里输入的内容。`network.hosts` 与 `media.hosts` 都是出口,要尽量窄,评审也会盯这两项。
- **用户在插件登录表单里输入的密码,会在提交时交给插件。** 宿主能保证输入框是原生的、插件画不出假框,但保证不了拿到密码的插件拿它做什么。所以只对信得过的插件输入密码;能用扫码或授权码的来源,应当优先用它们。
- **作者账号被盗。** 攻击者用被盗的账号发一个权限不变的新版本,它会被自动收录,并在约「索引刷新间隔 + 宿主刷新间隔」(小时量级)内静默安装。可行的缓解:新版本收录后先「冷却」一段时间再对所有用户推荐;让用户固定某个版本;让作者为发布启用两步验证与受保护标签。这些都还没设计。
- **CI 检查可以被绕过。** 插件可以探测到自己跑在检查环境里而表现得无害。
- 插件可以返回误导性的内容(假歌名、假推荐)。市场的人工评审和社区举报是对策,技术上无解。
- 来源服务本身的行为(登录风控、封号、条款)不由宿主控制。用户用自己的账号使用第三方客户端的风险由用户承担;插件作者有责任在描述里写明。
- 宿主的 wazero 运行时、系统 TLS、解码库自身的漏洞。依赖更新是宿主的日常职责。
- 同一系统用户下的其他本机程序,能读到钥匙串条目与同一用户目录下的文件(包括保险库与它的密钥文件)。
- **市场索引本身没有签名。** 宿主只核对「下载到的包」与「索引里记录的 sha256」是否一致,**不自己验证来源证明**——那是登记处 CI 在收录时做的。所以如果有人能篡改索引(例如拿到登记处仓库或 `mygo-music` 组织的写权限),就能把某个插件的下载地址和 sha256 一起换掉,宿主会照单安装。镜像同理:索引镜像提供的 sha256 也被完全信任(只有包的镜像可以靠索引里的 sha256 校验)。这一层的保护是账户安全:对 `mygo-music` 组织强制两步验证、收紧登记处仓库的写权限与分支保护。

## 7.8 报告漏洞

通过各仓库 `SECURITY.md` 里的私密渠道报告(GitHub Security Advisories),不要开公开 issue。(各仓库建立时补上。)
